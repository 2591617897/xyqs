## 私信页视频改为「点一下直接全屏播放」（00:20）

**诉求**：`pages/chat/index` 里别人（和自己）发的视频，原来气泡内是 `<video controls>` 小窗，点中央播放键只是内联播放；用户要点了就全屏。

### 改动
- `pages/chat/index.wxml`
  - 视频消息改成「封面卡」：`<video>` 关掉**全部**原生控件（`controls/show-center-play-btn/show-play-btn/show-fullscreen-btn/show-progress/enable-progress-gesture` 全 false），只负责渲染首帧
  - 上面盖一层 `.mv-hit`（透明铺满整卡，`catchtap="onTapVideo"`）+ 中央 `.mv-play` 白圈三角 + 右下 `.mv-dur` 时长
  - 页面末尾新增全屏播放层 `.vplayer`（`wx:if="{{vpShow}}"`、`catchtouchmove="noop"`）：顶部条 = 关闭键 + 「全屏播放中」，下方 `<video autoplay controls object-fit="contain" bindended="closeVideo">`
- `pages/chat/index.wxss`：`.msg-video` 变相对定位容器；`.mv-hit/.mv-play/.mv-dur`；`.vplayer/.vp-bar/.vp-close/.vp-body`
- `pages/chat/index.js`：`data.vpShow/vpUrl`；`onTapVideo / closeVideo / onVideoMeta / noop`；`fmtDuration()`；`onHide + onUnload` 收掉播放层（否则后台继续出声）
- `styles/icons.wxss`：新增 `.ico-play`（唯一新增图标，其余复用 `.ico-close`）
- 文档：`小程序项目档案.md` 的 `pages/chat/index` 一行补齐视频行为

### 关键决策（为什么这么写）
- **原生控件必须全关**：只要 `controls` 开着，点击落在原生控件层，`bindtap` 收不到，加 `bindtap` 也没用
- **热区铺满整卡而不是只包中央圆**：只盖圆的话用户点边上没反应；`.mv-hit` 透明铺满，点哪儿都进全屏
- **关闭键不能压在 video 上**：video 是原生组件，旧机型会盖住普通 view → 全屏层用「顶部条 96rpx + video 从 96rpx 往下」，关闭键永远在 video 区域之外，且布局不依赖 flex
- **时长自己算**：控件关掉后没人再显示 `00:02`，用 `bindloadedmetadata` 的 `e.detail.duration` 写回 `messages[i].durationText`
- 不改后端：私信表没有 poster/duration 字段，首帧靠 video 自身渲染，时长靠元数据，零迁移

## 内容可见范围（发闲置 / 发帖子加开关，默认仅本校，可切同市可见）

- 需求：发布页加「可见范围」开关，默认只限本校，切换后同市都能看

  可见范围是内容自己的属性。同名会让 OR 嵌套查询极易写错。
  公共常量 `campus-common/.../content/Visibility`（SCHOOL / CITY / normalize / isCity）

  两表 `visibility VARCHAR(16) NOT NULL DEFAULT 'school'`，历史 7 行自动回填 school（数据量小，无风险）
- 后端：Goods/Post 实体 + Req 加字段；`apply()` / `publish()` / `update()` 归一化落库；
  `page()` / `pageInternal()` 加过滤；新增 `assertVisible()` 在 `detail()` 校验（**404 而非 403**，不暴露内容存在性）
- 前端：`utils/visibility.js` + 两个发布页加选项卡片（默认 school、编辑回显、提交带 visibility）
- 自检 `scripts/visibility-selftest.js`（68 项）全绿；全量回归含 `db-schema-check`、`security-baseline-check` 均通过

```java

//    SQL 变成 "... AND (visibility = ? OR)" —— 整条 SQL 语法错误

// ✅ 拆成两个分支
```

## P0/P1 全部修复完成（2026-10-28 06:30）

### 关键设计决策（改前必读）
- **C 端令牌吊销**：`t_user.token_version` + JWT claim `tv` + **网关** `AccountStateChecker`（60s 缓存，回源失败 fail-open）。
  放网关而不是每个服务：一处覆盖全部服务，新增服务不会漏。`JwtService.create` **故意不留 3 参数重载**——留了就会签出 `tv=0`，对已 +1 的用户表现「刚登录就被踢」，让编译器守住这个坑。
- **封禁 403 / 版本旧 401 必须分开**：401 会被小程序当掉线自动清 token 再重登，封禁用户会陷入重登循环看不到原因。
- **升级兼容**：存量令牌无 `tv` → 按 0；库里 DEFAULT 0 → 不会踢人（已实测 200）。
- **`ClientIp`**：优先 `X-Real-IP`（Nginx 覆盖式写入，gateway 不改写它），再 XFF 首段，最后 remoteAddr。
  A/B 实测：X-Real-IP 固定 + XFF 轮换 35 次，旧代码 0/35 被限流（完全绕过），新代码第 31 次起 429。
- **广告计数**：请求路径零 DB 写，`AdMetricsService` 内存聚合 + 60s flush；曝光 10 分钟 / 点击 24h 按 IP 去重。
  需要 `@EnableScheduling`（已加在 `PostApplication`）。
- **`WriteRatePolicy`**（campus-common，`com.campus` 会被各服务扫到）：PUBLISH_POST 30s/30、WALL 60s/20、GOODS+DEMAND 120s/15、COMMENT 10s/200、REPLY 60s/30、CREATE_ORDER 10s/100。9 个写入口。

IDE 用 Eclipse 编译器（ECJ）时，**编译失败也会写 target/classes**，桩 class 里只有一句 throw。
Maven 默认增量编译只看「.class 是否比 .java 新」→ 看到 IDE 刚写的 class 就跳过编译
→ 桩 class 被原样打进 jar → 线上必 500，堆栈是 java.lang.Error 不是业务异常。
本次中招 4 个模块：auth(AuthService)、goods(2)、message(2)、post(1)。

### 处置
1. 停全部业务进程（Windows 下 jar 被占，`clean` 删不掉 target，构建会卡在 campus-wall）
2. `mvn -DskipTests clean install`（**必须 clean**）
3. 校验：target/classes 与每个 jar 的 BOOT-INF/classes 内 `Unresolved compilation problem` 均为 0
4. 用 jar 重启 8 个服务（auth/user/goods/wall/post/message/admin/gateway），冒烟全 200

### 防回退
- parent pom 加 `<useIncrementalCompilation>false</useIncrementalCompilation>` + 注释说明
- 新增 `scripts/check-build-artifacts.js`：查 target/classes、jar 内部桩代码 + build-jars 是否比 target 旧；注入探针验证过会 exit 1
- `build-jars/` 原为 10-27 旧包（缺 P0/P1 修复），已用 11 个新 jar 全量覆盖

### IDE 用户的注意点
IDE 直接跑 target/classes，不走 Maven，所以：改完代码必须 `mvn clean install` 或让 IDE「Build 委托给 Maven」；
否则 IDE 一旦编译报错又留下桩，重启多少次都还是同样的错。

## 首页卡片互动区改版：点赞胶囊 + 左浏览右图标（第三十六轮）

需求：把首页卡片的点赞换成参考图样式（对方是校园墙类小程序）。
原效果：底栏三格均分 `👁 4 / 👍 1 / ↗`。目标效果：点赞独立成灰底胶囊挂在正文下方，
底栏左侧「浏览 N」纯文字、右侧评论 + 分享图标靠右排。

### 硬约束（改这块前必读）
- **未点赞绝不能用 emoji 🤍**：emoji 颜色写死在字形里，白色心在 #f4f4f6 灰底上几乎不可见，
  且 `color` 对它无效（点赞态无法变色）。必须用文字符号 **♡ / ♥** + CSS color 控制
- **点赞胶囊必须始终渲染**：它是卡片上唯一的点赞入口（底栏已无点赞位）。
  0 赞时只隐藏**数字**（`wx:if="{{it.liked || it.likeCount > 0}}"`），胶囊本体不能隐藏
- **底栏不能用三列均分**：`flex:1` 均分把三个图标摊满整行、两端留白极大，与参考图的
  「左信息 + 右图标群」不是一个手感 → `justify-content:space-between` + `.zfoot-acts{margin-left:auto}`
- `.zcard` 是 `display:block`，所以 `.zlike` 用 `inline-flex` 宽度自动包裹内容；
  若哪天把卡片改成 flex column，`align-items:stretch` 会把胶囊拉满整行
- 评论数为 0 时不显示数字（`commentText !== '0'`），与参考图一致；需求卡显示 `replyCount`

### 交付
- `pages/index/index.wxml`：两处 foot 全部重写（今日最热卡 / 广场卡）；点赞胶囊 `.zlike`；
  底栏 `.zfoot` + `.zfoot-views` + `.zfoot-acts` + `.zfoot-btn`；需求卡右侧 `🙋 + replyCount`
- `pages/index/index.wxss`：新增 `.zlike / .zfoot / .zfoot-btn / .zfoot-share`；
  删除 `.zcard-foot / .zcard-act / .zcard-act-icon / .zcard-share` 全套旧样式（只有 index 用，无跨页影响）
- 数字统一 `font-variant-numeric: tabular-nums`，点赞数 9→10 时不抖动

### 验证
静态页按 1rpx=0.5px 渲染 + Playwright 截图核对排版（临时目录已删）；
`check-miniprogram` 24+16 页、`home-zones` 55、`mock` 170、`demand` 100、`visibility` 68、
`category-tidy` 40、`user-links` 25、`msg-subpackage`、`goods-search` 54 全绿。零后端改动。

### 修复（同日）：底栏图标没靠右
现象：截图里评论 + 分享卡在卡片中间。根因是**首页帖子没有 `viewCount`**，
左侧「浏览 N」`wx:if` 不渲染 → `.zfoot` 只剩一个子元素 →
`justify-content: space-between` 在单子元素时退化成 `flex-start`，`margin-left:auto` 也没顶住。

修法：加一层**始终存在的左槽位** `.zfoot-left { flex:1; min-width:0 }`，
它吃掉剩余空间把右侧图标推出右边缘；`.zfoot-acts` 再留 `margin-left:auto` 作双保险
（左槽位在时无空间可吸，不生效；结构变动时兜底）。
顺手把图标间距从 `flex gap` 换成 `.zfoot-share { margin-left:40rpx }`
—— gap 在低版本基础库/部分 iOS 上不生效，失效后两图标会粘在一起。
另：`.zfoot-share` 需同时清 `height/min-width`，button 默认尺寸会撑高底栏。

### 再修：图标间距消失（两图标粘连）
现象：图标靠右了，但「💬 1↗」三个元素挤成一团。
两个独立原因：
1. **间距写在 `button` 上不生效**：分享按钮是 `<button open-type="share">`，
   基础库组件内置样式的实际优先级压得过页面 class，`margin: 0 0 0 40rpx` 被吃掉。
   → 修法：**外面包一层普通 `<view class="zfoot-share-wrap">` 承载 `margin-left`**，
   button 只负责 `open-type="share"` 这个能力，盒模型压到最小（padding/width/min-width/height 全清）。
   `hover-class` 也要挪到 wrap 上，button 上写 `hover-class="none"` 避免默认灰底。
2. **`flex gap` 在部分 iOS WebView 不生效**：图标与数字间距也丢了。
   → 全项目这套互动区不用 `gap`，一律 `.zfoot-num / .zlike-num { margin-left: 8rpx }`。

⚠️ **结论写进红线**：小程序的 `button` 不要当普通容器用 —— 凡是需要 margin/padding 控制位置的地方，
外层包 view，button 只留语义能力（share / getPhoneNumber / openSetting）。

### 三修：箭头依然没贴右（真因是 button 的 width:184px）
上一轮把间距修好了，但箭头离卡片右边缘还有 64pt。量截图坐标才定位到真因：
**`.zfoot-acts` 其实早就贴右了，是箭头在 button 内部居中**。
微信 `button` 内置 `width:184px`（≈128pt）且压得过页面 class 的 `width:auto`，
箭头就在这 128pt 里居中 → 视觉上「没靠右」。

最终解法（不再和 button 盒模型较劲）：
- `.zfoot-share-wrap`：`position:relative; flex:none; width:44rpx; height:44rpx`，`margin-left` 控制与评论图标间距
- `.zfoot-share`：`position:absolute; left:0; top:0; width:100% !important; height:100% !important`
  + `min-width/max-width/margin/padding` 全部 `!important` 归零 —— 184px 无从发挥
- 点击热区仍是 44rpx 见方，正好盖住箭头

⚠️ **踩坑记录（三次）**：`button` 做分享/授权入口时，**任何盒模型属性（width / margin / padding / min-width）
写在 button 上都不要相信**。正确姿势：外层固定尺寸 wrap + button 绝对定位铺满，布局属性全挂 wrap。
这条比「外层包 view 就行」更硬 —— 只包 view 但不锁 button 宽度，箭头仍会在 128pt 里居中。

### 三修（终）：图标与 button 彻底解耦
最终结构：
```xml
<view class="zfoot-share-wrap" hover-class="share-hover">
  <text class="zfoot-ico">↗</text>
  <button class="zfoot-share-hit" open-type="share" hover-class="none"></button>
</view>
```
- `.zfoot-share-wrap`：`position:relative; flex:none; width/height:44rpx; justify-content:flex-end;
  align-items:center; margin-left:36rpx` —— 图标右对齐贴齐内容区右边缘，热区仍向左留 44rpx
- `.zfoot-share-hit`：`position:absolute; left/top:0; width/height:100%!important;
  min-width:0!important; max-width:none!important; margin/padding:0!important; opacity:0` —— 纯透明点击层

**关键认知**：图标一旦放在 button 内部，它的水平位置就由 button 的盒子决定；
只要 button 的 184px 宽度有任何机会生效，图标就永远「看起来没贴右」。
所以正确做法不是调 button 的样式，而是**让 button 里不再有内容**。

### 再改（用户反馈）：点赞胶囊要回到同一排，图标换成 QQ 那套
用户给了 QQ 群（校园墙）截图：底栏是「浏览 1262 ... 😊 8 ▢19 ↗」**一行**四元素，
而我们把点赞做成正文下方独立胶囊 → 互动区分裂成两排，用户不接受。
另一条意见是「图标也不一样」：我们用的 💬 / ↗ 是彩色 emoji + 文字符号，
对方是单色线性图标。

**最终结构（一行）**：`浏览 N`（左槽位 flex:1 顶右）+ 右侧
`♡/♥ [数字]` · `方泡内嵌数字` · `SVG 弯箭头`。

⚠️ **教训**：点赞不要从互动栏里移出去。它一旦独立成行，互动区就有两排，
用户在「点赞要到哪一行」上会来回摇摆 —— 参考图里那个 ❤️7 🐶1 胶囊是
**QQ 的表情回应展示**，不是点赞按钮；点赞按钮是底栏那个笑脸，本来就在一排。

### 图标选型（这次踩过就不要再换）
- 点赞 **♡ / ♥ 文字符号**：可被 `color` 控制，灰→粉状态变化看得见。
  **绝不用 emoji ❤️/🤍**：颜色写死在字形里，白心在浅底上几乎不可见

  和另外两个图标不是一个视觉体系
  ⚠️ data-uri 里 `#` 必须转义成 `%23`，否则 url 被当锚点截断，图标直接不显示

### 其他

- 需求卡不显示点赞（是「人回应」不是社交互动），回应数用同一个方泡
