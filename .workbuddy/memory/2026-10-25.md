## 图片地址没跟着换域名（头像仍请求 192.168.0.102）
- 现象：`ACTIVE_ENV='prod'`（`https://campus-api.trkcwl.com`）后接口都通，但 Network 里图片请求仍是
  `http://192.168.0.102:8888/uploads/...`（头像是灰块）。
- 根因：库里的图片地址是**上传那一刻写死的绝对地址**；前端只有部分字段调了 `resolve`，
  **`avatar` 系列全漏了**（`pages/index/index.js` 的 `avatar: p.authorAvatar`、`g.sellerAvatar`、`hot.authorAvatar`，
  以及 space/profile 等页面），所以内网地址原样进了 `<image src>`。
  另外用户编辑器里的 `port: 8888` 是未保存的改动（磁盘上是 `''`，https 必须走 443）。
- 修复（一次覆盖全站）：`utils/request.js` 新增 `normalizeImages(v, depth)`，
  对**响应体递归**把含 `/uploads/` 的字符串统一 `resolveImg()` 换成本次 `SERVER`；
  `mock` 与真实分支的成功回调都改成 `resolve(normalizeImages(body.data, 0))`。
  页面里原有的 `resolveList` 保留（幂等，重复调用无副作用）。
- 实测：假响应体
  `{avatar:'http://192.168.0.102:8888/uploads/a.jpg', images:['http://127.0.0.1:8888/uploads/b.jpg'], cover:'https://images.unsplash.com/x.jpg', note:'hello'}`
  → 前两个变成 `https://campus-api.trkcwl.com/uploads/...`，外链与普通字符串**不受影响**。
- 校验：`node --check utils/request.js`、`mock-selftest` 139/139。临时测试文件已删。
- 遗留可选：DB 里历史绝对地址仍是内网 IP（前端已归一，不影响显示）；
  想彻底干净可把 `t_user.avatar` / `t_post.author_avatar|images` / `t_goods.seller_avatar|images`
  统一 `UPDATE ... = REPLACE(url, 'http://192.168.0.102:8888', '')` 存成相对路径。

## 「头像更新不生效」= 上传成功但 /uploads/ 404（2026-10-25 02:20）
- 现场：库 `t_user.avatar` 已是 `https://campus-api.trkcwl.com/uploads/2026/10/880a1503....jpeg`，
  服务器文件管理器里文件也在（`112.54.138.12:/mnt/ssd/web/campus-api.trkcwl.com/uploads/2026/10/`，4.41KB），
  但 `curl https://campus-api.trkcwl.com/uploads/2026/10/880a1503....jpeg`
  → **HTTP 200 + `{"code":404,"msg":"资源不存在"}`**（Spring 的 JSON，不是图片）。
  `<image>` 拿到 JSON 解码失败 → 显示为空/灰块，所以「头像没变」。
- 结论：**写入了 A 目录、静态资源却从 B 目录读**。`UploadController` 与 `WebConfig` 用的是同一个
  `campus.upload.dir`，同进程内不可能不一致 → 只可能是 ① 进程工作目录与预期不同（`./uploads` 相对路径），
  或 ② **Nacos 里残留多个 campus-user 实例**，上传打到一个实例、读取被负载均衡到另一个。
- 代码加固（`campus-user`）：
  - `WebConfig` 启动时校验目录：不存在 → warn；不可读 → error（并提示 /uploads 会 404），
    同时仍打印 `[upload] 静态资源映射 /uploads/** -> file:/...`，**这行是定位这类问题的关键**
  - `UploadController` 落盘后校验 `target.isFile() && length>0`，失败直接抛「图片保存失败」并打绝对路径
- 交付建议（已写进 nginx 模板与 README）：**`/uploads/` 交给 Nginx alias 直出**
  `alias /mnt/ssd/web/campus-api.trkcwl.com/uploads/;`（末尾斜杠必须），
  上传目录与读取路径统一由 Nginx 决定，彻底绕开工作目录/Nacos 多实例问题，且更快。
  同时 `UPLOAD_DIR` 必须用绝对路径。
- 校验：`mvn -pl campus-user compile` 通过。线上仍需用户改 Nginx 或排查 Nacos 实例后重启。

## 上传目录改为「jar 同目录」解析（2026-10-25 02:24）
- 用户反馈「jar 项目和 uploads 同级」，但仍 404。根因认知纠正：**`./uploads` 相对的是进程工作目录
  （cwd），不是 jar 所在目录**；systemd `WorkingDirectory` / `cd && java -jar` / 从别处 `nohup java -jar`
  三种 cwd 完全不同 → 写读分家。
- 新增 `campus-user/.../config/UploadPaths.java`：统一解析规则，**写入（UploadController）与读取（WebConfig）
  用同一个方法**，从机制上杜绝「上传 200、图片 404」：
  - 绝对路径 → 原样
  - 相对路径 + 以 jar 运行（codeSource 以 `.jar` 结尾）→ 按 **jar 所在目录**解析（jar 与 uploads 同级即正确）
  - 相对路径 + IDE/classes → 退回 cwd（避免写进 `target/`，本地行为不变）
- `WebConfig` 启动日志升级为：
  `[upload] 静态资源映射 /uploads/** -> file:/...（配置 dir=./uploads，进程工作目录=/xxx）` —— 一次就能看出是否分家；
  目录不可读时打 ERROR。`UploadController` 仍保留落盘后 `isFile() && length>0` 校验。
- README 增补「上传目录（jar 与 uploads 同级）」表格说明三种运行方式的解析结果。
- 校验：`mvn -pl campus-user compile` 通过。**需重新打包部署 campus-user**。

## 首页频道 / 表白墙分类支持左右滑动切换
- 新增 `miniprogram/utils/swipe.js`：纯手势识别（无 wx API，可单测）。有效横滑需同时满足
  横向位移 ≥60px、横向 ≥ 纵向×1.6、时长 ≤600ms；`move` 阶段纵向已占优就直接放弃，让位页面滚动
- 为什么不用 `<swiper>`：首页/表白墙都是**页面级滚动 + 下拉刷新 + onReachBottom 分页**，
  换 swiper 要把内容塞进定高 scroll-view，下拉刷新和分页全要重做 → 只做手势，命中后走与点 tab 完全相同的逻辑
- 绑定位置：内容区包一层 `.swipe-area`（`bindtouchstart/move/end/cancel`），**不含**横向 scroll-view
  （nav-scroll / cat-scroll 自己横滑，绑在祖先会误切频道）
- 首页：`switchChannelOffset(±1)`，频道序列 = `[''].concat(channels.map(String))`；到两端 toast 提示
- 表白墙：`switchCatOffset(±1)`，cats 顺序即「精选表白 → 树洞 → 寻物 → 捞人」
- 附带：nav-scroll / cat-scroll 加 `scroll-into-view`（`navInto` / `catInto`），滑动切换后选中 chip 自动滚进可视区
- 附带：两个页面 `loadData`/`load` 加请求序号 `_loadSeq`，旧请求回来不覆盖新结果（快速滑动必备）；
  表白墙 `load` 的 reset 分支允许打断上一轮（原来 `if (loading) return` 会让「切了分类但列表没变」）
- 校验：`node --check` 3 个 JS、WXML 标签闭合、check-miniprogram、mock-selftest 139/139；
  另用 6 组手势模拟验证方向映射（左滑=下一个，纵向/斜向/慢拖/微动不触发）
