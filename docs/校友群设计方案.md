## 零、实施记录与偏差（v2.1，2026-10-27）

### 0.1 两项待确认已定稿

| 项 | 结论 |
|---|---|
| WebSocket 上线顺序 | **与业务一起做**（阶段一同时交付 WS + 轮询兜底），理由：WS 的补拉/降级本身依赖 HTTP 接口，分轮反而重复改前端 |
| 群管理员阶段一权限 | **只给「夜间静音豁免 + 发言频率豁免 + @所有人」**；删消息 / 禁言（单人限言）留在阶段二 |

### 0.2 偏差：Redis → 进程内实现（重要）

原设计假定项目有 Redis（ticket 存 `SET NX EX`、频控双闸、`PUBLISH ws:broadcast` 跨实例广播）。
**实际本项目没有任何 Redis 依赖，6379 端口也未监听**（`LoginRateLimiter` 同样是进程内滑动窗口）。故全部改为进程内实现：

| 能力 | 原设计（Redis） | 实际实现 | 代价 / 何时换回 Redis |
|---|---|---|---|
| WS ticket | `SET ws:ticket:{u} {userId} EX 60` + `GETDEL` | `WsTicketService`，`ConcurrentHashMap` + `@Scheduled` 清理，`consume()` 用 `remove()` 天然 GETDEL | 单实例没问题；多实例时必须换 Redis `SET NX EX` + `GETDEL`，否则 A 实例发的票在 B 实例校验失败 |
| 发言频率 | Redis 计数器双闸 | `GroupRatePolicy`，进程内 `ConcurrentHashMap` 记录 `lastAt` / 当日计数，`@Scheduled` 清理 | **多实例会把阈值放大 N 倍**（每实例各算一份）。横向扩容前必须换 Redis |
| 禁言缓存 | Redis | `GroupMuteService`，60s `ConcurrentHashMap`（**null 结果也缓存**，否则高频空查会打穿 DB） | 多实例间有 ≤60s 生效延迟，可接受 |
| 跨实例广播 | Redis Pub/Sub `ws:broadcast` | `WsBroadcaster` 只推本实例在线连接 | **多实例部署前必须补 Redis Pub/Sub**，否则 A 实例发的消息 B 实例的在线用户收不到（但重连补拉 / 轮询能兜住，不会丢消息） |

> 结论：**当前单实例部署功能完整可用**。上多实例（或加 Redis）时按上表逐项替换，接口签名不用改。

### 0.4 实施中踩到并已修掉的问题

## 二、产品设计

### 2.1 群的组织

```
一所学校 = 一个校友群
群名：{学校名}校友群          例：贵州大学校友群
群主：系统（无人工群主），由后台管理员代管
管理员：后台可指定该校用户为群管理员（role=1）
成员：该校所有 schoolId 匹配的用户，绑定即入群
```

### 2.2 万人群的真实瓶颈

技术不是瓶颈，**阅读体验**才是。

| 指标 | 假设值 |
|---|---|
| 注册用户 | 10,000 |
| 日活 DAU | 2,000（20%） |
| 峰值同时在线 | 600（DAU 30%，21:00–22:00） |
| 日发消息 | 2,400 条 |
| **峰值流速** | **8 条/分钟**（约 7.5 秒一条，可读） |
| 极端情况 | 50 条/分钟（开学季） |

三道闸门控制流速：
1. **频率自适应收紧**（群越大个人间隔越长，见 7.1）
2. **默认静默**——群里说话不推送通知，用户主动进群看，天然降低焦虑
3. **未来拆子群**——成员 >3000 且流速 >30 条/分时按学院拆（`parent_group_id` 已预留）

### 2.3 用户旅程

```
① 注册 → 昵称头像 → 选学校（school-onboard）
        ↓ PUT /user/me { schoolId }
   自动入群（用户无感知）+ 学校无群则自动建群
        ↓
② 消息页 → 「贵州大学校友群」卡片（未读/@ 角标）
        ↓
③ 首次进群 → 全屏群规 + 安全提示 → 「我已知晓，进群」
        ↓
④ 群里聊天（WS 实时）
        ↓
⑤ 被 @ → 角标 +1（默认只有 @ 才提醒）
        ↓
⑥ 点头像 → 资料卡 → 发私信（复用现有 1v1）
```

### 3.2 连接鉴权：一次性 ticket（关键设计）

**为什么不能把 JWT 直接放 URL**：
- 小程序 `wx.connectSocket` 无法可靠自定义请求头
- 只能放 query，而 **Nginx access_log 会记录完整 URL**
- 长期 JWT 落进日志 = 拿到就能冒充用户，且有效期 72 小时

**方案：短期一次性 ticket**

```
① POST /api/groups/ws-ticket   （带正常 JWT header）
   → { "ticket": "9f3a...", "expiresIn": 60 }

② wx.connectSocket({ url: `wss://campus-api.trkcwl.com/api/ws?ticket=9f3a...` })

③ 服务端握手时：GETDEL ws:ticket:{ticket}  → 拿到 userId
   - 不存在 / 已用过 / 过期 → 拒绝握手（关闭连接）
   - 命中 → 建立连接，绑定 userId
```

- ticket 存 Redis，`SET ws:ticket:{uuid} {userId} EX 60`，**用 `GETDEL` 保证一次性**
- 泄露了也无害：60 秒过期 + 用一次就废
- ticket 里不带任何权限信息，只是"换 userId 的凭证"

> ⚠️ **网关必须放行 `/api/ws/**`**：WebSocket 握手请求不带 `Authorization` 头，如果 `AuthGlobalFilter` 照常拦截会直接 401，握手失败。放行后的安全边界由 `GroupWsHandler` 的 ticket 校验兜住——这条要在代码注释里写清楚，否则后人会以为网关漏了一个口子。

### 3.3 网关与 Nginx 配置

**网关（`application.yml` 新增）**

```yaml
- id: campus-ws
  uri: lb:ws://campus-message
  predicates:
    - Path=/api/ws/**
  filters:
    - StripPrefix=1
```

**Nginx（`deploy/nginx-campus-api.trkcwl.com.conf` 新增 location）**

```nginx
# WebSocket：必须单独一段，光靠 location / 的 proxy_http_version 1.1 不够
location /api/ws {
    proxy_pass http://campus_gateway;
    proxy_http_version 1.1;

    # 这两行是握手升级的关键，缺一行就 400/连接立刻断开
    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection "upgrade";

    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # 默认 60s 无数据就断，心跳 30s 一次能维持；这里放宽到 1 小时
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
}
```

> ⚠️ 现有 `location /` 只有 `proxy_http_version 1.1`，**没有 Upgrade 头**。如果不加独立 location，WebSocket 握手会失败，表现为"连接立刻断开"，且 Nginx 日志只有 101 或 400，极难排查。这是本项目最容易漏的一步。

### 3.4 多实例广播（Redis Pub/Sub）

用户连在哪个实例是随机的，A 实例发的消息必须能送到 B 实例的连接上。

```
发布：PUBLISH ws:broadcast  {"groupId":"...","message":{...}}
订阅：每个实例都订阅 ws:broadcast
      → 解析出 groupId
      → 查本机 byGroup[groupId]
      → 本机没有该群连接就跳过（绝大多数情况）
      → 有则逐个 send
```

```java
// WsBroadcaster
public void broadcast(Long groupId, Object payload) {
    redis.convertAndSend("ws:broadcast", JSON.toJSONString(Map.of(
            "groupId", String.valueOf(groupId),          // 雪花必须转字符串
            "message", payload)));
}

// 每个实例的订阅者
@RedisListener(channel = "ws:broadcast")
public void onBroadcast(String json) {
    Payload p = parse(json);
    Set<WsSession> sessions = registry.sessionsOfGroup(Long.valueOf(p.groupId));
    if (sessions == null || sessions.isEmpty()) return;   // 本机没人，直接跳过
    for (WsSession s : sessions) s.sendText(json);
}
```

**为什么不用 `PSUBSCRIBE ws:group:*` 动态订阅**：订阅/取消订阅要在连接进出群时维护，状态复杂易错；而 1w 人规模消息量只有 8 条/分钟，全量广播的开销完全可以忽略。**简单可靠优先。**

### 3.5 连接管理与心跳

```java
// WsSessionRegistry（本机索引，ConcurrentHashMap）
Map<String, WsSession> bySessionId;          // sessionId → 会话
Map<Long, Set<WsSession>> byGroup;           // groupId → 本机该群连接（广播用）
Map<Long, Set<WsSession>> byUser;            // userId → 该用户所有连接（多端）
```

**心跳**：小程序**不支持发送协议级 ping/pong 帧**，只能走业务层消息。

```
服务端每 30s 发 {"type":"ping"}
客户端回 {"type":"pong"}
60s 未收到 pong → 判定死连接 → 关闭并清理索引
```

> ⚠️ 清理必须同时从 `byGroup` 和 `byUser` 三个索引里移除，漏一个就是内存泄漏。这是 E-09 的典型场景。

**容量**：单条 WebSocket 连接约占 30~50KB。3000 并发 ≈ 150MB 堆，单实例可承受；超过 5000 需要多实例（Redis 广播已支持，直接横向扩）。

### 3.6 断线重连与消息补拉（最关键的用户体验点）

**WebSocket 相比轮询的固有缺点：断线期间的消息会丢。** 必须补。

```js
// 小程序端
onSocketClose() {
  this.reconnectDelay = Math.min((this.reconnectDelay || 1000) * 2, 30000)
  setTimeout(() => this.connect(), this.reconnectDelay)   // 1s→2s→4s→8s→16s→30s
},

onSocketOpen() {
  this.reconnectDelay = 1000
  // ★ 补拉断线期间的消息，这是不漏消息的唯一保证
  if (this.data.lastId) {
    this.pullSince(this.data.lastId)
  }
}
```

**降级兜底**：连续 3 次重连失败 → 自动切 HTTP 轮询（8s），WS 恢复后切回。保证弱网下功能不瘫。

### 3.7 消息投递全流程

```
① 用户点发送
② 前端乐观插入本地气泡（id = "local-xxx"）
③ WS send { type:"msg", clientMsgId, content, atUserIds, atAll }
④ 服务端校验链：
      单人禁言 → 夜间静音 → 发言频率 → SecurityGuard.checkText
⑤ 落库 t_group_message（client_msg_id 唯一键幂等）
⑥ 更新 t_group.last_msg_id / last_msg_text / last_msg_time
⑦ 处理 @（见第五章）
⑧ Redis PUBLISH ws:broadcast
⑨ 各实例推给本机该群在线连接
⑩ 发送者收到自己的消息 → 按 clientMsgId 匹配，**替换** local 气泡
   其他人收到 → 追加气泡
```

> 自己发的消息也走广播（不特判），前端靠 `clientMsgId` 去重替换。这样代码只有一条路径，不会出现"自己发的和别人收到的格式不一致"。

### 4.2 五个关键设计说明

**① 未读数用 `last_read_id` 游标 + `LIMIT 100`，不 `COUNT(*)`**

```sql
-- 最多扫 100 行，走 idx_group_id
SELECT id FROM t_group_message
WHERE group_id=? AND id > ? AND sender_id != ? AND deleted=0
LIMIT 100
-- 返回 <100 = 精确值；=100 → 前端显示「99+」
```

**② `@所有人` 绝不能给 1 万人各写一行**

```
❌ 错误做法：UPDATE t_group_member SET mention_unread = mention_unread + 1 WHERE group_id=?
   → 1 万行更新，锁表 + 主从延迟 + undo log 膨胀
✅ 正确做法：只更新 t_group.last_at_all_msg_id = {msgId}
   → 未读判断：last_at_all_msg_id > member.last_read_id
   → 零写放大，一次主键更新
```

`@指定人` 才写 `t_group_mention`，而且**一次最多 @ 10 人**，写 10 行完全没问题。

**③ `client_msg_id` 幂等**：WS 断线重发很常见，唯一键冲突时捕获后返回已存在那条（与项目 `t_follow` 的处理模式一致，catch 里必须直接 return）。

**④ `notify_mode` 默认 0 = 仅 @ 提醒**

这是本轮的核心产品决策：**群里有人说话不打扰，只有被点名才提醒**。1 万人群如果默认全提醒，用户第一天就会关掉通知甚至卸载。

**⑤ 归档表去掉 `uk_client`**：归档数据不再接收新写入，唯一键纯属浪费空间，只保留 `(group_id, id)` 查询索引。

## 五、@提醒与通知策略

### 5.1 三种提醒来源

| 来源 | 存储方式 | 写放大 | 展示 |
|---|---|---|---|
| **@我（指定）** | `t_group_mention` 一行 + `mention_unread +1` | 最多 10 行/条 | 具体数字（如 "@3"） |
| **@所有人** | `t_group.last_at_all_msg_id` | **0 行** | 「@全体」角标，实时算条数 |
| 普通群消息 | 无 | 0 | 只有红点（`last_msg_id > last_read_id`） |

**@所有人未读数的实时算法**（量极小，走 `idx_group_atall`）：

```sql
SELECT COUNT(*) FROM t_group_message
WHERE group_id=? AND at_type=2 AND id > ? AND deleted=0
-- @所有人 一天通常 0~2 次，COUNT 开销可忽略
```

**总 @ 数** = `mention_unread` + `@所有人未读条数`。

### 5.2 谁能 @ 谁

| 操作 | 权限 | 限制 |
|---|---|---|
| @指定人 | 所有成员 | 只能 @ 群内成员；单条消息**最多 @ 10 人** |
| @所有人 | **仅 `role >= 1`（群管理员）** | 每人每天最多 3 次，防滥用刷屏 |

> @所有人 是权力，必须限量。1 万人群体一天被 @ 五次，用户会直接静音群，那时候你所有的提醒设计都白做了。

### 5.3 提醒触达方式（阶段划分）

| 通道 | 阶段一 | 说明 |
|---|---|---|
| 群卡片角标 | ✅ | 消息页群卡片右上角 |
| 底栏「消息」红点 | ✅ | 复用现有 `custom-tab-bar` 未读角标 |
| 小程序内消息中心 | ✅ | 群会话条目 |
| 微信服务通知（订阅消息） | ❌ 阶段二 | 项目订阅消息目前只做到"授权"层，还没做服务端发送（见档案待办），群聊提醒要等这条链路打通 |

> ⚠️ 要跟用户说清楚：**阶段一的"提醒"只在小程序内生效**，用户不打开小程序看不到。真正的"推送到微信"要等订阅消息发送能力建好。不要承诺做不到的事。

### 5.4 前端 @ 交互

```
输入框打「@」 → 弹出成员选择器（可搜索，1w 人必须支持搜索）
             → 选中 → 输入框插入「@昵称 」+ 记录 userId 到 atUserIds
             → 发送时带上 atUserIds = ["id1","id2"]
群管理员额外看到「@所有人」按钮
```

**展示**：消息气泡里 `@昵称` 高亮成蓝色可点（点了跳对方资料卡）。

## 六、自动入群与自动建群

### 6.1 三个绑定学校入口（一个都不能漏）

实查 `campus-user/UserService.java`：

| # | 入口 | 位置 | 场景 |
|---|---|---|---|
| 1 | `PUT /user/me` | 约 228 行 | **新用户引导选校**（主入口） |
| 2 | `POST /user/verify` | 约 255 行 | 学生证认证 |
| 3 | `POST /user/verify/wx-student` | 约 324 行 | 微信学生认证 |

**三处都挂** `afterSchoolBound()`，漏一处的后果是「用户认证了但群里没他」，且**不报错**，用户只会觉得群没人。

### 6.2 实现：抽公共方法 + fail-soft

```java
private void afterSchoolBound(Long userId, Long schoolId, String schoolName) {
    if (schoolId == null) return;
    try {
        groupJoinClient.autoJoin(new AutoJoinReq(userId, schoolId, schoolName));
    } catch (Exception e) {
        // 入群失败不能影响「绑学校」主流程；兜底见 6.4
        log.warn("自动入群失败 userId={} schoolId={}: {}: {}",
                 userId, schoolId, e.getClass().getSimpleName(), e.getMessage());
    }
}
```

> ⚠️ **必须在 `userMapper.updateById(user)` 之后调用**。放前面事务未提交，message 服务通过 Feign 查到的是旧数据。

### 6.3 自动建群 + 并发安全

```java
@Transactional(rollbackFor = Exception.class)
public Long autoJoin(Long userId, Long schoolId, String schoolName) {
    Group group = groupMapper.selectByTypeAndKey(1, String.valueOf(schoolId));
    if (group == null) group = createGroupQuietly(schoolId, schoolName);

    GroupMember m = memberMapper.selectOne(group.getId(), userId);
    if (m != null) {
        if (m.getStatus() == 1) return group.getId();
        // status 0（被踢）/ 2（主动退）：尊重结果，不自动拉回
        return group.getId();
    }
    insertMember(group.getId(), userId);
    groupMapper.incrMemberCount(group.getId(), 1);
    return group.getId();
}

/**
 * 并发建群：1 万人同时绑定时多个线程会同时判定「群不存在」。
 * 靠 uk_type_key 唯一键兜底，冲突者重查。
 * ⚠️ catch 里必须直接 return 重查结果 —— 继续往下走会重复插成员。
 */
private Group createGroupQuietly(Long schoolId, String schoolName) {
    try {
        Group g = new Group();
        g.setType(1);
        g.setBizKey(String.valueOf(schoolId));
        g.setSchoolId(schoolId);
        g.setName((schoolName == null || schoolName.isEmpty() ? "本校" : schoolName) + "校友群");
        g.setNotice("欢迎来到本校校友群！可以找同学、问课程、拼车回家、互通消息。"
                  + "请友善发言，禁止广告与人身攻击，违规会被禁言。");
        groupMapper.insert(g);
        return g;
    } catch (DuplicateKeyException e) {
        return groupMapper.selectByTypeAndKey(1, String.valueOf(schoolId));
    }
}
```

**校名从哪来**：`AutoJoinReq` 带上 `schoolName`（`campus-user` 侧本来就要查学校存在性），省一次跨服务调用。

### 6.4 双保险：进群页 lazy join

```java
// GET /groups/{id} 开头
GroupMember me = memberMapper.selectOne(groupId, userId);
if (me == null) {
    if (Objects.equals(mySchoolId(userId), group.getSchoolId())) {
        autoJoin(userId, group.getSchoolId(), group.getName());   // 自愈补加入
        me = memberMapper.selectOne(groupId, userId);
    } else {
        throw new BizException("你不在这个群里");
    }
}
```

### 6.5 换校与退群

| 场景 | 处理 |
|---|---|
| 未认证用户改 schoolId | 退旧群（`status=2`）+ 入新群 |
| 已认证用户换校 | 现有逻辑已禁止，无需处理 |
| 主动退群 | `status=2`，**不再自动拉回**，入口显示「重新加入」 |
| 被管理员踢出 | `status=0`，不自动加回，页内提示「你已被移出本群」 |

> ⚠️ **只有「完全没有成员记录」才自动加入**。`status=2` 和 `status=0` 都不参与，否则用户退了又被拉回来，是最伤体验的 bug。

## 七、管控机制

### 7.1 发言频率（按群规模自适应）

| 群成员数 | 间隔 | 每日上限 | 理论峰值（2000 日活） |
|---|---|---|---|
| ≤ 500 | 10s | 50 | — |
| 501 ~ 2,000 | 20s | 40 | 100 条/分 |
| 2,001 ~ 5,000 | 40s | 30 | 50 条/分 |
| > 5,000 | **60s** | 20 | **33 条/分** |

```java
public RateLimit resolve(Group g) {
    if (g.getRateGapSec() > 0) {          // 群级配置优先（后台可强制覆盖）
        return new RateLimit(g.getRateGapSec(), g.getRateDayMax() > 0 ? g.getRateDayMax() : 50);
    }
    int n = g.getMemberCount();
    if (n <= 500)  return new RateLimit(10, 50);
    if (n <= 2000) return new RateLimit(20, 40);
    if (n <= 5000) return new RateLimit(40, 30);
    return new RateLimit(60, 20);
}
```

**Redis 双闸**

```
闸一（间隔）：SET group:rate:{gid}:{uid}:gap 1 NX EX {gapSec}
             → null = 冷却中，用 TTL 取剩余秒数回给前端
闸二（日限）：INCR group:rate:{gid}:{uid}:day:{yyyyMMdd}，首次 EXPIRE 90000
```

Redis 不可用 → **降级放行** + warn（频率限制是增强能力，不能变成"Redis 挂了全站发不了言"）。

**群管理员豁免**：`role >= 1` 不受间隔限制（但仍受内容审核约束）。

### 7.2 夜间静音（后台可按群单独配置）

**默认 `00:30 ~ 06:30` 开启**，三个可调维度都在 `t_group` 上：

| 字段 | 默认 | 后台可改 |
|---|---|---|
| `night_enabled` | 1（开） | ✅ 可按群关闭 |
| `night_start` | `00:30` | ✅ 可按群单独设 |
| `night_end` | `06:30` | ✅ 可按群单独设 |

```java
// 跨天判断：复用 MessageSettingService#inDnd 的既有实现（支持 23:00-07:00 跨零点）
boolean nightMute = group.getNightEnabled() == 1
        && TimeRange.inRange(now, group.getNightStart(), group.getNightEnd());

if (nightMute && member.getRole() >= 1) nightMute = false;   // 管理员豁免
```

**为什么默认不是 23:00**：用户是大学生，23:00–00:30 是全天最活跃时段，掐掉等于砍一半流量。00:30 既不影响正常交流，又能挡住深夜刷屏和风险内容。

**前端三处必须做对**：
1. 输入框上方常驻提示条「本群 00:30–06:30 夜间静默，可浏览不可发言」
2. 输入框置灰但**保持可滚动浏览**
3. **不能等用户打完字点发送才拒绝**——这是最差的体验

### 7.3 禁言（判定顺序不能错）

```
1. 单人禁言？  → 「你已被禁言至 {时间}，原因：{原因}」
2. 夜间静音？  → 「本群 00:30-06:30 夜间静默」
3. 频率超限？  → 「发言太频繁，请 N 秒后再试」
4. 内容审核    → 「内容包含违规信息」（SecurityGuard 抛 400）
```

顺序错了会给用户错误的拒绝理由（比如明明被禁言 3 天，提示"发言太频繁"）。

**缓存**：`group:mute:{gid}:{uid}` → `"endAt|reason"`，TTL 到禁言结束，避免万人群每次发言都查库。

**时长选项**：1 小时 / 24 小时 / 7 天 / 永久（`end_at = NULL`）。

## 八、首次入群引导（安全提醒 + 发言规则）

### 8.1 触发条件

`t_group_member.rules_agreed = 0` 时，进群首屏弹**全屏引导层**（不是 toast，不是半屏弹窗——要用户真的看完）。

### 8.2 内容结构

```
┌───────────────────────────────────┐
│         贵州大学校友群              │
│         1,024 位校友在这里          │
├───────────────────────────────────┤
│ 🛡 安全提醒                        │
│ · 不要透露学号、身份证、住址等个人信息 │
│ · 谨防冒充同学的借钱、代付、刷单诈骗   │
│ · 交易请走平台，勿私下转账            │
├───────────────────────────────────┤
│ 📋 发言规则                        │
│ · 禁止广告、刷屏、人身攻击、违法内容   │
│ · 每人每 10 秒可发 1 条，每天最多 50 条│
│ · 00:30–06:30 为夜间静默，可浏览不可发 │
│ · 违规内容将被删除并可能被禁言         │
├───────────────────────────────────┤
│ 遇到违规内容？长按消息可举报           │
├───────────────────────────────────┤
│      [ 我已知晓，进入群聊 ]           │
└───────────────────────────────────┘
```

**动态文案**：频率和静音时段要**从接口读群配置拼**，不能写死。群管理员改了时段，引导页要跟着变。

### 8.3 落库

```http
POST /groups/{id}/agree-rules
→ UPDATE t_group_member SET rules_agreed = 1 WHERE group_id=? AND user_id=?
```

> **存后端不存本地**：换手机、清缓存后不该重复弹；用户点"已知晓"是法律意义上的告知确认，本地存储没有证据效力。

### 8.4 审核价值

这套引导同时是**提审加分项**。社交类目审核关注"是否有内容管理措施"，群规 + 举报入口 + 禁言机制三件套齐全，能显著降低被驳回概率。以微信官方最新审核规范为准。

## 十、数据库自动归档

### 10.1 策略

| 项 | 值 |
|---|---|
| 保留窗口 | **12 个月**（热表） |
| 执行频率 | 每 24 小时一次（`fixedDelay`，不是 cron——重启后能自动补上） |
| 单批大小 | 500 条（避免长事务锁表） |
| 迁移目标 | `t_group_message_archive` |
| 关联处理 | 同步迁移对应 `t_group_mention`（否则 @ 提醒会指向不存在的消息） |

### 10.2 实现（照 `SearchLogCleanTask` 的既有模式）

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class GroupMessageArchiveTask {

    private final GroupArchiveService archiveService;

    /** 启动 5 分钟后跑第一次，之后每 24 小时一次 */
    @Scheduled(initialDelay = 5 * 60_000L, fixedDelay = 24 * 3600_000L)
    public void run() {
        try {
            int total = 0;
            while (true) {
                int moved = archiveService.moveBatch(500);   // 迁移一批
                if (moved == 0) break;
                total += moved;
                Thread.sleep(200);                            // 让主库喘口气
            }
            if (total > 0) log.info("[group-archive] 归档 {} 条 12 个月前的群消息", total);
        } catch (Exception e) {
            // 归档失败不能影响业务，下次再跑
            log.warn("[group-archive] 归档异常: {}", e.getMessage());
        }
    }
}
```

```java
// GroupArchiveService
@Transactional(rollbackFor = Exception.class)
public int moveBatch(int limit) {
    LocalDateTime before = LocalDateTime.now().minusMonths(12);

    // 1. 取一批待归档（走 created_at 索引或按 id 范围）
    List<GroupMessage> batch = messageMapper.selectOlderThan(before, limit);
    if (batch.isEmpty()) return 0;

    // 2. 先插归档表（幂等：INSERT IGNORE，重复跑不会报错）
    archiveMapper.insertBatch(batch);
    List<Long> ids = batch.stream().map(GroupMessage::getId).toList();

    // 3. 迁移关联的 @ 记录（不做的话 @ 提醒会指向已删消息）
    mentionArchiveMapper.moveByMessageIds(ids);

    // 4. 删热表
    messageMapper.deleteByIds(ids);
    return batch.size();
}
```

### 10.3 四个必须注意的点

| # | 点 | 原因 |
|---|---|---|
| 1 | **`@EnableScheduling` 必须加在 `MessageApplication` 上** | 不加注解 `@Scheduled` 不生效，**而且不报错**（项目 `GoodsApplication` 的注释里已经记录过这个坑） |
| 2 | 分批 + `Thread.sleep(200)` | 一次性迁百万行会锁表、撑爆 undo log、主从延迟飙升 |
| 3 | `INSERT IGNORE` + `DELETE` 而非 `INSERT...SELECT...DELETE` 一条 SQL | 分两步才能在中间失败时重试不丢数据 |
| 4 | `fixedDelay` 不用 `cron` | 服务器重启错过窗口能自动补上，不依赖精确时间点 |

### 10.4 归档后的行为

- 用户翻历史翻到 12 个月前 → 接口返回「更早的消息已归档」，不报错
- @提醒指向已归档消息 → 点进去提示「该消息已归档」
- **不提供归档数据查询接口**（真要查走后台 SQL），避免多一层复杂度

```js
// 单例 + 自动重连 + 降级
let socket = null, retry = 0, listeners = {}

function connect() {
  http.post('/groups/ws-ticket').then(({ ticket }) => {
    socket = wx.connectSocket({
      url: `wss://campus-api.trkcwl.com/api/ws?ticket=${ticket}`
    })
    socket.onOpen(() => { retry = 0; emit('open') })
    socket.onMessage(({ data }) => {
      const msg = JSON.parse(data)
      if (msg.type === 'ping') return send({ type: 'pong' })
      emit(msg.type, msg)
    })
    socket.onClose(() => {
      emit('close')
      retry++
      const delay = Math.min(1000 * Math.pow(2, retry), 30000)
      setTimeout(connect, delay)          // 指数退避
      if (retry >= 3) emit('degrade')     // 连续失败 → 上层切轮询兜底
    })
    socket.onError(() => { /* onClose 会跟着触发 */ })
  }).catch(() => {
    // 拿不到 ticket（如未登录）→ 降级
    emit('degrade')
  })
}
```

**五个必须做对的细节**：

| # | 细节 | 不做会怎样 |
|---|---|---|
| 1 | `onHide`/`onUnload` 关连接 + 清定时器 | 后台持续占连接，耗电 |
| 2 | 重连成功先**补拉** `sinceId` | 断线期间消息永久丢失 |
| 3 | 自己发的消息按 `clientMsgId` **替换**而非追加 | 一条消息显示两次 |
| 4 | 上滑翻历史时不强制滚到底 | 看历史被拽回底部 |
| 5 | `setData` 只传增量片段 | 消息上百条必卡（E-02） |
