## 一、结论摘要

| 问题 | 结论 |
|---|---|
| 能不能实现 | **能**。项目已有内容安全（`SecurityGuard`）、私信（`MessageService`）、举报（`pages/report`）、社区规范（`pages/legal/rule`），群聊是横向扩展而非从零搭 |
| 最大风险 | 不是技术，是**产品结构**。两个"全局大群"会退化成人人刷屏的死群，必须按学校 / 城市自动分群 |
| 实时方案 | **阶段一用 HTTP 增量轮询**（复用现有轮询模式），预留 WebSocket 升级路径 |
| 工作量估算 | 阶段一核心可用约 3~4 个开发日；阶段二（成员/@/后台管控）另算 |
| 审核风险 | 中等。群聊属 UGC 高敏感区，内容审核必须落库前同步拦；同城群要淡化"陌生交友"属性 |

## 二、必须先纠正的设计前提：不是「两个群」，是「两个维度 × N 个群」

### 2.1 问题

用户描述的是「校友群、市友群两个大群」。若真做成两个全局群：

| 后果 | 说明 |
|---|---|
| 彻底刷屏 | 贵州省高校数万人进一个群，消息每秒几十条，用户打开只能看到滚动条在飞 |
| 语义错误 | "校友群"里混着贵州大学、贵州师大、各职院的人——谁也不认识谁，"校友"名不副实 |
| 审核一颗雷 | 一个大群出违规内容，处置手段只有「整群封禁」，等于全站下线 |
| 数据表扛不住 | 单群消息表日均数万条，无上限增长 |

### 2.2 正确结构

```
校友群  = 按 schoolId 分群  →  用户进的是「贵州大学校友群」
市友群  = 按 city 分群      →  用户进的是「贵阳同城群」
```

**规模测算（贵州）**：高校约 70~80 所 → 校友群 ~80 个；市州 9 个 → 同城群 9 个。合计约 90 个群，单群日活几十到几百人，完全可控。

**这个结构你项目天然支持**：
- `utils/scope.js` 已有 school / city 两档浏览范围
- `t_school.city` 已存州府（都匀/凯里/兴义）
- `utils/school.js#PREFECTURE_SEAT` 已处理"自治州 → 州府"映射，同城群归属直接复用

### 2.3 未绑定学校的用户（已知坑）

项目档案明确记录：`schoolId = null` 时"本校"筛选会退化成看全站。
群聊里同样存在——这类用户点「校友群」不能给他看空群或全站群，**必须引导去选学校**，复用现有 `school-onboard` 组件的引导路径。

## 三、技术选型：实时消息怎么送

这是本方案唯一有真实分歧的决策点。

| 维度 | 方案 A：HTTP 增量轮询 | 方案 B：WebSocket + Redis Pub/Sub |
|---|---|---|
| 现有基础 | ✅ 私信已 4s 轮询（`pages/chat/index.js`），模式现成 | ❌ 全项目零 WebSocket，需从零搭 |
| 后端改动 | 新增 1 个增量查询接口 | ws 处理器 + 心跳 + 多实例 Redis 广播 + 鉴权握手 |
| 网关改动 | 加一条 `/api/groups/**` HTTP 路由 | 需 `lb:ws://` 路由 + `AuthGlobalFilter` 放行逻辑重写 |
| Nginx 改动 | 无 | 必须加 `proxy_set_header Upgrade/Connection`，否则握手失败 |
| 消息延迟 | 3~5s（可调至 2s） | < 500ms |
| 服务端压力 | 每在线用户每 5s 一个请求；1000 人在线 ≈ 200 QPS，按 `(group_id,id)` 索引查增量，压力极小 | 常驻连接，内存占用高但 QPS 低 |
| 小程序端成本 | 无额外权限 | 需 `wx.connectSocket`，要求 **wss** + 微信后台配 socket 合法域名 + 前后台切换重连 + 弱网断线检测 |
| 故障半径 | 单次请求失败无感，下一轮自动补上 | 断线期间消息全丢，必须有重连 + 补拉逻辑 |
| 迁移代价 | 接口按 `sinceId` 游标设计，换传输层不改业务代码 | — |

> ✅ **推荐方案 A（HTTP 增量轮询）**，适用于当前「约 90 个群、单群峰值几十到几百人」的规模。
>
> **判断依据**：WebSocket 的收益是「延迟从 4s 降到 0.5s」，成本是「网关 + Nginx + 多实例广播 + 弱网重连」四套新增复杂度。对校园社区群聊，4s 延迟用户无感；而对一个尚无运维冗余的项目，多一套长连接基础设施就是多一类线上故障。**等单群同时在线稳定超过 500 人再升级。**

**两方案共用的前提**：绝对不能复用现有 `GET /messages/{id}` 那种「返回整个会话全量记录」的模式。群消息必须**游标增量拉取**，否则一次请求就是几百 KB。

## 四、数据模型

群聊**不能复用** `t_message_conversation` / `t_message`：私信模型的 `user_a/user_b` 和 `receiverId` 在群里语义不成立。新建 4 张表。

```sql
-- ============ 1. 群定义 ============
CREATE TABLE IF NOT EXISTS t_group (
  id            BIGINT       NOT NULL COMMENT '雪花 id',
  type          TINYINT      NOT NULL COMMENT '1 校友群(按学校) 2 同城群(按城市)',
  biz_key       VARCHAR(64)  NOT NULL COMMENT 'type=1 存 school_id 字符串；type=2 存 city 名',
  name          VARCHAR(64)  NOT NULL COMMENT '群名，如「贵州大学校友群」',
  avatar        VARCHAR(255) DEFAULT '' COMMENT '群头像',
  notice        VARCHAR(500) DEFAULT '' COMMENT '群公告',
  member_count  INT          NOT NULL DEFAULT 0 COMMENT '成员数冗余',
  status        TINYINT      NOT NULL DEFAULT 1 COMMENT '1 正常 0 停用',
  -- 运营配置：每个群独立，便于出问题时只收一个群的权，不用全站停服
  rate_gap_sec  INT          NOT NULL DEFAULT 10  COMMENT '同一人两次发言最小间隔（秒）',
  rate_day_max  INT          NOT NULL DEFAULT 50  COMMENT '同一人每日发言上限',
  night_start   CHAR(5)      NOT NULL DEFAULT '00:30' COMMENT '夜间静音开始 HH:mm',
  night_end     CHAR(5)      NOT NULL DEFAULT '06:30' COMMENT '夜间静音结束 HH:mm',
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_type_key (type, biz_key),
  KEY idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='群定义';

-- ============ 2. 群成员 ============
CREATE TABLE IF NOT EXISTS t_group_member (
  id           BIGINT   NOT NULL,
  group_id     BIGINT   NOT NULL,
  user_id      BIGINT   NOT NULL,
  role         TINYINT  NOT NULL DEFAULT 0 COMMENT '0 普通 1 管理员 2 群主',
  last_read_id BIGINT   NOT NULL DEFAULT 0 COMMENT '已读游标（关键：群消息不逐条标已读）',
  join_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  status       TINYINT  NOT NULL DEFAULT 1 COMMENT '1 在群 0 已退出/被踢',
  PRIMARY KEY (id),
  UNIQUE KEY uk_group_user (group_id, user_id),
  KEY idx_user (user_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='群成员';

-- ============ 3. 群消息（独立表） ============
CREATE TABLE IF NOT EXISTS t_group_message (
  id            BIGINT       NOT NULL COMMENT '雪花 id，天然递增 → 直接当游标用',
  group_id      BIGINT       NOT NULL,
  sender_id     BIGINT       NOT NULL,
  sender_name   VARCHAR(32)  NOT NULL DEFAULT '' COMMENT '昵称快照，由 refreshAuthors 覆盖为最新',
  sender_avatar VARCHAR(255) NOT NULL DEFAULT '' COMMENT '头像快照，同上',
  type          VARCHAR(16)  NOT NULL DEFAULT 'text' COMMENT 'text / image / system',
  content       VARCHAR(1000) NOT NULL,
  deleted       TINYINT      NOT NULL DEFAULT 0 COMMENT '1 已撤回（软删）',
  created_at    DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_group_id (group_id, id DESC)   -- 增量查询核心索引，必须建
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='群消息';

-- ============ 4. 单人禁言 ============
CREATE TABLE IF NOT EXISTS t_group_mute (
  id          BIGINT       NOT NULL,
  group_id    BIGINT       NOT NULL,
  user_id     BIGINT       NOT NULL,
  start_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  end_at      DATETIME     DEFAULT NULL COMMENT 'NULL = 永久（直到手动解除）',
  reason      VARCHAR(128) NOT NULL DEFAULT '',
  operator_id BIGINT       NOT NULL DEFAULT 0 COMMENT '0 = 系统自动（如举报命中）',
  status      TINYINT      NOT NULL DEFAULT 1 COMMENT '1 生效 0 已解除',
  PRIMARY KEY (id),
  KEY idx_group_user_status (group_id, user_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='群禁言记录';
```

### 三个关键设计说明

**1. `last_read_id` 而不是逐条 `read_flag`**
私信是 1 对 1，`t_message.read_flag` 可行。群消息是一对多——500 人 × 每条消息一行已读标记 = 表爆炸。
改成每人一个**已读游标**：未读数 = `COUNT(id > last_read_id AND sender_id != me)`。一条 SQL 搞定，表不增长。

**2. 雪花 id 直接当游标**
项目 ID 生成用 `IdType.ASSIGN_ID`（雪花，时间有序）。因此 `id` 天然按时间递增，`WHERE group_id=? AND id > ? ORDER BY id` 即增量拉取，不需要额外 `seq` 字段。

**3. 运营配置放在群表上**
`rate_gap_sec` / `night_start` 等挂在每个群而不是全局常量——某个群出问题，只调那一个群，不用全站改配置重启。

## 五、接口设计

```
GET  /groups                        我的两个群（按当前用户 schoolId / city 解析）+ 各自未读数
GET  /groups/{id}                   群详情：群信息 + 我的禁言状态 + 是否夜间静音 + 频率配置
GET  /groups/{id}/messages          增量拉取  ?sinceId=&limit=30
POST /groups/{id}/messages          发消息    {type, content}
POST /groups/{id}/read              上报已读游标 {lastId}
GET  /groups/{id}/members           成员列表 ?page=&size=（阶段二）
```

### 5.1 增量拉取的语义（核心）

```java
// sinceId = 0  → 首次进群，返回最新一页（倒序取 limit 条后反转）
// sinceId > 0  → 返回比它新的消息（正序）
@GetMapping("/{id}/messages")
public R<GroupMsgPageVO> messages(@PathVariable Long id,
                                  @RequestParam(defaultValue = "0") Long sinceId,
                                  @RequestParam(defaultValue = "30") Integer limit) {
    // limit 硬上限 50，防前端传 1000 拉爆
    // 返回 { list, hasMore, lastId, mute: {active, until, reason} }
}
```

- 增量一次最多返 50 条，超出置 `hasMore=true`
- 前端拿 `hasMore=true` 时显示吸底条「还有新消息 ↓」，点击继续拉，**不强行滚动**（用户可能正在翻历史）
- 轮询时若无新消息返回空数组，响应体 < 200 字节

### 5.2 未读数（不能每次 COUNT 全表）

「我的群列表」需要两个群的未读数。用游标算：

```sql
SELECT COUNT(*) FROM t_group_message
WHERE group_id = ? AND id > ? AND sender_id != ? AND deleted = 0
```

走 `(group_id, id)` 索引，是范围扫描 + 计数，单群数据量在万级内完全够。
若某群消息量超过 10 万，再换 Redis 计数器（写时 INCR，读时直接取）。

## 六、四大管控机制

### 6.1 发言频率限制（Redis 双闸）

```
第一闸 最小间隔：SET group:rate:{gid}:{uid}:gap 1 NX EX {rate_gap_sec}
                返回 false → 拒绝，429「发言太频繁，请 N 秒后再试」
第二闸 每日上限：INCR group:rate:{gid}:{uid}:day:{yyyyMMdd}（首次 EXPIRE 90000）
                超过 rate_day_max → 拒绝，429「今日发言已达上限」
```

- Redis 不可用时**降级放行**（与 `SecurityGuard` 的 fail-open 一致），但记 warn
- 拒绝时返回剩余秒数，前端显示倒计时按钮态，不要只弹一次 toast

### 6.2 内容审核（硬门槛）

复用项目现有链路，**落库前同步拦**：

```java
// 新增业务类型常量
public static final String BIZ_GROUP_MSG = "GROUP_MSG";

// 发消息入口，必须在 insert 之前
securityGuard.checkText(userId, content, SecurityGuard.SCENE_FORUM, SecurityGuard.BIZ_GROUP_MSG);
// 命中 → 抛 BizException(400)，不落库；违规记录自动进 t_content_audit（source=2）
// 图片消息：securityGuard.checkImages(userId, BIZ_GROUP_MSG, null, List.of(url))
```

⚠️ **项目已知坑，群聊沿用即可**：`msg_sec_check` / `media_check_async` 对 chunked POST 会直接回 HTTP 412，必须用 JDK `HttpClient` + `BodyPublishers.ofString`。这条已在 `campus-auth` 里解决，群聊走同一个 `SecurityGuard`，天然继承，不用重踩。

### 6.3 禁言（单人 + 夜间）

**判定顺序（顺序错了会给出错误的拒绝理由）**：

```
1. 单人禁言生效？  → 「你已被禁言至 xxx，原因：xxx」
2. 夜间静音时段？  → 「本群 00:30-06:30 为夜间静默，可浏览不可发言」
3. 频率超限？      → 「发言太频繁，请 N 秒后再试」
```

```java
// 夜间跨天判断，直接复用 MessageSettingService#inDnd 的跨天逻辑（已写好，支持 23:00-07:00 跨零点）
boolean nightMute = inRange(now, group.getNightStart(), group.getNightEnd());
```

**夜间禁言的三条实战建议**（这是产品决策，我按经验给判断）：

1. **别默认 23:00 开始**。你的用户是大学生，23:00~00:30 是全天最活跃时段，这个点掐掉等于砍掉一半流量。文档里默认值我写的是 **00:30~06:30**。
2. **管理员豁免**。夜间群里有违规内容需要处置，管理员也不能发言就只能等天亮。
3. **前端要提前告知**，不要等用户打完字点发送才弹拒绝。输入框上方常驻一条浅色提示条，输入框置灰但保留"浏览"能力。

### 6.4 点头像私聊

完全复用现有 `POST /messages/start`，零后端改动：

```
群聊页点头像
  → 弹出迷你资料卡（头像 / 昵称 / 学校 / 认证标 + 「发私信」按钮）
  → 调 POST /messages/start { peerId }
  → 拿到 conversationId
  → navigateTo /pages/chat/index?id={conversationId}
```

要点：
- **不要直接跳 `/pages/chat/index?peer=`** 让它自己补建会话——现有兜底逻辑可用，但会多一次往返且失败时静默。显式 `start` 拿到 id 再跳更稳。
- 点**自己的**头像不弹卡片（或只显示"这是我"）。
- 资料卡里带一个「举报」入口，这是审核加分项。

## 七、前端页面与轮询策略

### 7.1 页面清单

| 页面 | 路径 | 位置 | 说明 |
|---|---|---|---|
| 消息中心（改造） | `pages/messages/index` | 主包 | 顶部加两张群卡片（校友群 / 同城群），带未读红点 |
| 群聊天页 | `subpackages/msg/group/chat` | **分包** | 核心页面，消息列表 + 输入区 + 禁言条 + 资料卡弹层 |
| 群成员 | `subpackages/msg/group/members` | 分包 | 阶段二 |

**必须进分包**：群聊页有消息列表、输入区、禁言提示条、资料卡弹层、图片预览，体积不小。主包已有 23 页，别碰 2MB 红线。同步在 `app.json` 的 `preloadRule` 里给 `pages/messages/index` 加上 `subpackages/msg`（已有配置，只需把新页面加入子包 pages 数组）。

### 7.2 轮询策略（照抄私信的成熟写法，改参数）

```js
// 与 pages/chat/index.js 同构，只是间隔从 4s 放宽到 5s（群消息量更大）
onShow() {
  if (this._pollTimer) return
  this._pollTimer = setInterval(() => this.pullIncrement(), 5000)
},
onHide() { this.stopPoll() },      // ⚠️ 必须清理，否则后台一直请求
onUnload() { this.stopPoll() },

pullIncrement() {
  if (this._fetching || this.data.sending) return   // 防重入，私信页已有此保护
  this._fetching = true
  http.get(`/groups/${gid}/messages?sinceId=${this.data.lastId}`, null, { silent: true })
    .then(res => { this._fetching = false; this.appendMessages(res) })
    .catch(() => { this._fetching = false })
}
```

**三个必须做对的细节**：

1. **用户上滑翻历史时不强制滚到底**。判断「当前滚动位置距底部 < 一屏」才自动滚动，否则显示吸底新消息条。私信页用 `_lastMsgId` 做同类判断，思路一致。
2. **自己发的消息要同步游标基线**。发送成功后把 `lastId` 更新到最新，否则下一轮轮询会把自己刚发的消息当成"新消息"重复滚动（私信页 `postMessage` 里已经处理过这个坑）。
3. **发送走乐观更新**：本地先插一条 `local-` 前缀气泡，成功后用服务端返回替换，失败则移除并提示。群聊延迟敏感度比私信高，这一步体感差距明显。

## 八、审核合规风险（以微信官方最新规范为准）

| 风险点 | 说明 | 应对 |
|---|---|---|
| 类目 | 群聊属 UGC 即时交流，落在「社交-社区/论坛」类目下 | 项目已按此申报，无需加类目，但要确认最新类目要求 |
| 内容安全 | 群聊是审核最关注的场景，一条违规可能全站下架 | 落库前同步拦（已有 `SecurityGuard`）+ 图片异步送审 |
| 举报闭环 | UGC 必须有可触达的举报入口 | 复用 `pages/report`，在群消息长按菜单 + 资料卡各挂一个 |
| 用户协议 | 进群前需用户已知悉社区规范 | 首次进群弹一次《社区规范》确认，复用 `pages/legal/rule` |
| **同城社交属性** | "市友群"如被判定为「陌生人交友」，审核口径会收紧 | 命名为「XX 同城校园生活」，定位为校园生活交流，**不要出现"交友""约"等表述** |
| 未成年人 | 校园场景可能含未成年用户 | 夜间静音本身就是保护措施，可在协议中说明 |

> 以上类目与审核口径以微信官方最新规则为准，提审前建议再对一遍 `docs/微信审核自查清单.md`。

## 九、分阶段落地

### 阶段一：核心可用（约 3~4 个开发日）

| # | 任务 | 产出 |
|---|---|---|
| 1 | 建表 + 自动建群脚本 | `sql/migration-xxx-group.sql`，按现有学校 / 城市批量生成 90 个群 |

## 附：为什么不用现成的 IM SDK

考虑过腾讯云 IM（TIM）等第三方方案，判断是**不用**：

| 维度 | 自建（本方案） | 腾讯云 IM |
|---|---|---|
| 成本 | 0（复用现有服务） | 按 DAU 计费，且群聊消息有单独配额 |
| 用户体系 | 直接复用现有 JWT / 用户表 | 需双向同步用户，多一套账号体系 |
| 内容审核 | 已有 `SecurityGuard` 直接接 | 需配置第三方回调，链路更长 |
| 禁言/夜间静音 | 完全自定义 | SDK 群禁言能力有限（不支持夜间时段这种自定义策略） |
| 数据归属 | 自己库，随时查随时改 | 数据在第三方，导出受限 |
| 引入成本 | 3~4 天 | 接入 + 联调 + 用户同步约 2~3 天，但后续受制于人 |

结论：校园社区规模下，自建更划算，且审核与管控策略能完全贴合你的需求。

## 十一、群维度选题决策：只做校友群（2026-10-27 定）

### 11.1 决策

**做校友群（按 `schoolId`），不做市友群。** 且校友群按学校**灰度开**，不是 81 个群一次性全开。

### 11.2 依据：库里真实分布（2026-10-27 实查）

| 分组 | 学校数 | 城市数 | 说明 |
|---|---|---|---|
| 贵州 9 市州 | 46 | 9 | 极不均：贵阳 24、都匀 5、铜仁 5、遵义 4、凯里 2、安顺 2、毕节 2、六盘水 1、兴义 1 |
| 省外 21 城 | 35 | 21 | 平均每城 **1.67 所** |

`t_school` 共 **81 所**，贵阳一城占 24 所（29.6%），其余 8 个地州合计仅 22 所。

### 11.3 为什么不做市友群（三条硬伤）

**① 密度陷阱 —— 只有贵阳有密度**

按 `city` 分群会产出约 **30 个城市群**：贵阳 1 个（24 所学校，唯一有潜力）、8 个地州群（1~5 所学校）、**21 个省外城市群（平均 1.67 所学校）**。
后 29 个群，从建群那天起就是死群——这不是运营问题，是数学问题。

**② 省外城市群 100% 是死群**

北京 4 所、成都 4 所、上海 3 所、广州 3 所……这些是字典里的外地高校，不是核心用户。给它们建「北京同城群」，等于主动制造 20 个空房间。

**③ 没有身份纽带 + 审核风险**

- 校友群有 `schoolId` 背书：同校、同宿舍楼、同选课系统，社交动机明确（找同学、问课程、拼车回家、找老乡）
- 同城群只有「在同一个城市」，实质是**跨校陌生人社交**——微信对此审核口径最紧，且与「社交-社区/论坛」类目下"校园社区"的定位不符

### 11.4 校友群的三个额外优势

| 优势 | 说明 |
|---|---|
| 绕开 city 的三个已知坑 | `PREFECTURE_SEAT` 自治州→州府映射、IP 定位 key 配额、`city` 空值降级——做市友群要全部重踩一遍，做校友群一个都不用碰 |
| 与学籍体系同源 | `verifyStatus=2` 学籍认证、`schoolId` 筛选、「本校」浏览范围全都是现成的，群成员身份天然可信 |
| 与品牌叙事一致 | 项目名「校聚**一城**」，"校"在前；群聊是校园社区的延伸，不是同城交友平台 |

### 11.5 真正的敌人不是"选哪个群"，是冷启动

**实查：`t_user` 当前仅 2 个用户。**

在这个体量下，81 个校友群同时开 = 81 个空群。用户点进去看到"还没有人说话"，得到的结论是「这 app 没人用」——**死群比没有群更伤产品**。

**执行策略：按学校灰度**

| 阶段 | 开群范围 | 未开通学校的用户看到什么 |
|---|---|---|
| 阶段一 | 用户量 Top 1~3 的学校（先从贵阳头部校开始） | 「你学校的群正在筹备中」+ 引导去逛树洞/闲置，**绝不给空群** |
| 阶段二 | 扩到贵阳 24 所 | 同上 |
| 阶段三 | 视活跃度铺开地州 | 同上 |

**冷启动配套（比功能本身更重要）**：

1. **种子内容**：开群前由官方号 / 群主预置 3~5 条真内容（本周校园活动、失物招领、拼车回家、考研自习室占座情况），不要留空
2. **从现有功能导流**：树洞"求助"帖、闲置"面交"场景，天然适合引导进群（"同校拼车进群聊"）
3. **群公告写清"这个群是用来干嘛的"**：没有明确用途的群，用户不知道说什么

### 11.6 如果将来一定要做同城维度

**不要做成聊天室，做成信息流。** 同城真正有人需要的是"贵阳哪里能兼职""凯里哪家理发店靠谱"——这是**信息聚合**，不是实时聊天。

届时形态应是「同城互助」话题流（可复用现有 `t_post` + `t_channel` 结构），而不是复刻 QQ 群。真要做聊天室，前提是单城用户量足够撑起活跃度。

### 11.7 对技术方案的影响

- 数据模型不变（`t_group.type` 保留 1/2 两个枚举值，将来要加同城群不用改表）
- 建群脚本只按 `type=1` 生成，`biz_key = CAST(school_id AS CHAR)`
- 页面入口只放**一张**群卡片（「我的学校群」），不做"两个群"的双卡片布局
- 未绑定学校用户：入口显示引导去选学校（复用 `school-onboard`），不是给空群
