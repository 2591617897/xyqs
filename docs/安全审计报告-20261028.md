## 一、P0 级（先修这三条，其余都可以排队）

### P0-1 封禁 / 注销对 C 端完全失效（严重）

**位置**
- `campus-user/.../service/UserService.java#loginOrCreate`（第 74 行起）
- `campus-common/.../client/dto/UserBrief.java`（缺 `status` 字段）
- `campus-auth/.../service/AuthService.java#login`（拿到 UserBrief 后不校验状态）

**成因（三处叠加，缺一处都不至于这么严重）**

1. `UserBrief` 只带了 `id / nickname / avatar / schoolId / verifyStatus / cancelledAt`，
   **没有 `status`** —— 认证服务即使想校验也拿不到。
2. `loginOrCreate` 只按 `platform + openid` 查用户，**不判 `status=0`**，
   也不查 `t_user_blacklist`。封禁用户重新打开小程序 → `wx.login` → 换到全新令牌。
3. JWT 里没有版本号（C 端 `JwtService.create` 只写 `sub/iss/aud/typ/schoolId/vs`），
   签出去就收不回。后台封禁只是改库，**对已签发的令牌没有任何影响**，有效期 72 小时。

**实测路径**

```
① 后台封禁用户 A（t_user.status=0）
② A 用旧令牌 POST /api/wall/posts   → 200，发布成功（内容服务不查 status）
③ A 杀掉小程序重进 → POST /api/auth/login → 200，拿到新令牌（有效期 72h）
④ 循环 ②③ 可无限持续
```

**影响**：违规账号无法真正停用。配合「封禁后仍可发布」，
等于举报-封禁流程只有心理作用；注销同理（内容服务不判 `cancelledAt`）。

**修复方案（建议一次做完，约 1.5 小时）**

```java
// 1) UserBrief 补字段
private Integer status;      // 1 正常 / 0 封禁
private Long tokenVersion;   // 与 t_user 同名列，缺失按 0 处理

// 2) AuthService.login：拿到 user 后立刻拦
if (user.getStatus() != null && user.getStatus() == 0) {
    throw BizException.forbidden("账号已被封禁，如有疑问请联系管理员");
}

// 3) JwtService.create 增加 tv claim；封禁/解封/改密时 t_user.token_version + 1
.claim("tv", tokenVersion)

// 4) SecurityAutoConfig 注入身份时一并比对库里的 token_version
//    （后台 AdminAuthInterceptor 已有完全相同的实现，照抄即可）
```

> 若不想动 JWT 结构，最小可用方案是只做 1)+2)：封禁用户不能再登，
> 旧令牌最多 72 小时后自然失效。但「封禁后仍能发 72 小时内容」对内容型产品不可接受，
> 建议连 `tv` 一起做。

### P0-2 `X-Forwarded-For` 取第一段 → IP 维度限流全部可绕过（高危）

**位置**
- `campus-auth/.../service/AuthService.java#clientIp`（第 456 行）
- `campus-admin/.../service/AuthService.java#clientIp` / `AdminPasswordResetService#clientIp`
- `deploy/nginx-campus-api.trkcwl.com.conf`（`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`）

**成因**
`$proxy_add_x_forwarded_for` 的语义是「在**客户端自带的 XFF 后面追加**真实 IP」：

```
客户端发：X-Forwarded-For: 1.2.3.4
Nginx 转出：X-Forwarded-For: 1.2.3.4, 真实IP
后端取 split(",")[0] → 1.2.3.4   ← 攻击者自己填的
```

攻击者每次请求换一个伪造值，`LoginRateLimiter` 的 `ip:` 桶永远是新桶，
30 次/分钟的限制形同虚设。同理后台找回密码的「单 IP 1 小时 20 次」也可绕过。

**影响**：登录接口可被无限刷（openid 维度还能挡一层，但那是拿到 code 之后），
`code2Session` 日配额可能被耗尽 → 全站登录不可用；后台发码接口变成邮件轰炸机。

**修复方案（二选一，推荐 A）**

```nginx
# A. 只在最外层入口信任真实来源（推荐）：直接覆盖，不追加
proxy_set_header X-Forwarded-For $remote_addr;   # 替代 $proxy_add_x_forwarded_for
proxy_set_header X-Real-IP       $remote_addr;
```

```java
// B. 后端取最后一段（离服务器最近、由 Nginx 写入、不可伪造）
String[] parts = xff.split(",");
return parts[parts.length - 1].trim();
```

> 若将来前面再加 CDN，用 A 方案需要改成 `real_ip_header X-Forwarded-For` +
> `set_real_ip_from CDN网段`，这是标准做法，不易写错。

### P0-3 生产环境把异常根因原样返回给客户端（高危）

**位置**：`campus-common/.../exception/GlobalExceptionHandler.java` 第 56-62 行

```java
@ExceptionHandler(Exception.class)
public R<Void> handleOther(Exception e) {
    log.error("服务器异常", e);
    // 开发环境返回根因 message，方便定位；生产环境（R.fail 统一文案）不暴露   ← 注释这么写
    String devMsg = e.getCause() != null && e.getCause().getMessage() != null
            ? e.getCause().getMessage() : e.getMessage();
    return R.fail(500, "服务器开小差了: " + (devMsg == null ? "" : devMsg.substring(0, 200)));  // ← 但代码无条件拼接
}
```

**成因**：注释描述的「生产不暴露」**根本没有实现**，没有任何 `@Profile` / 开关分支，
`devMsg` 无条件拼进响应体。

**影响**：SQL 异常会带出表名/列名/约束名（如 `Duplicate entry '138xxxx' for key 'uk_phone'`
——顺带泄露手机号），NPE 会带出内部类名与行号，文件异常会带出服务器绝对路径。
这是渗透测试里最常被直接采信的「信息泄露」项。

**修复方案**

```java
@Value("${campus.error.expose-detail:false}")
private boolean exposeDetail;   // 生产默认 false，本地 application-local.yml 置 true

@ExceptionHandler(Exception.class)
public R<Void> handleOther(Exception e) {
    log.error("服务器异常 uri={}", request.getRequestURI(), e);  // 细节只进日志
    if (!exposeDetail) {
        return R.fail(500, "服务器开小差了，请稍后重试");
    }
    String msg = e.getCause() != null ? e.getCause().getMessage() : e.getMessage();
    return R.fail(500, "服务器开小差了: " + (msg == null ? "" : msg.substring(0, Math.min(200, msg.length()))));
}
```

## 二、P1 级（本轮新引入，建议同批修）

### P1-1 广告曝光/点击是「公开写库」且无去重 → 刷量 + 写放大（高危）

**位置**
- `campus-post/.../service/OperateService.java#materials` → `countView`
- `campus-post/.../service/OperateService.java#click`
- 网关 `AuthGlobalFilter`：`/api/ads` 在 `PUBLIC_READ_PREFIX`，`PUBLIC_AD_CLICK` 精确放行 POST

**成因**
每次公开 GET 广告位，对返回的**每一条**素材执行一次
`UPDATE t_ad_material SET view_count = view_count + 1`；点击接口同样直接 `+1`。
两个入口都**不需要登录、不去重、不采样、不限流**。

**影响**
1. **数据失真**：一条 `for i in {1..10000}; do curl -X POST .../click; done` 就能把点击量刷到十万，
   广告主看到的转化率是假的（这个模块是要给商家看的，数据不可信等于功能作废）。
2. **可用性**：1000 rps 的 GET 会打出 3000 次/秒的行更新，`t_ad_material` 行锁竞争会拖慢整个 campus-post。

**修复方案（按成本递增，选一即可）**
- 最小：`click` 落一张 `t_ad_click_log(material_id, ip_hash, day)`，唯一键去重；
  `view` 改成「同一 IP+素材 10 分钟内只记一次」（进程内 LRU 即可，与项目现有 `LoginRateLimiter` 同思路）。
- 更好：`view_count` 改成异步聚合（写内存计数，定时 60s flush），彻底消除公开 GET 的写库路径。

### P1-2 C 端内容发布完全没有频控（中高危）

**位置**：`campus-wall#WallService`、`campus-post#PostService`、`campus-goods#GoodsService/DemandService`
的发布方法（`requireVerifiedUserId()` 之后直接落库）

**成因**：项目里唯一的内容频控是校友群的 `GroupRatePolicy`（群聊 10~60 秒间隔 + 日上限），
**发帖 / 树洞 / 闲置 / 需求四条主线一个都没有**。只有 `SecurityGuard#checkText` 内容审核，
而它拦的是「违规词」，不拦「合法但高频」。

**影响**：一个已认证账号可在 1 分钟内发满整屏，把真实内容挤下去；
配合「发布即建号」可低成本刷存在感。这是最容易被真实用户投诉的问题。

**修复方案**：把 `GroupRatePolicy` 抽象成通用的 `WriteRatePolicy`
（用户维度：发帖 60s/次、日 20 条；闲置 5 分钟/次、日 10 条；树洞 5 分钟/次、日 10 条），
在四个 Service 的发布入口各调一行。项目无 Redis，沿用进程内实现并在注释里标注「多实例需换 Redis」。

### P1-3 用户上传无配额、无频控（中危）

**位置**：`campus-user/.../controller/UploadController.java`

**现状**：魔数校验 + 5MB 图片 / 50MB 视频上限都做了，这块是扎实的。
但**没有「每个用户每天多少次 / 多少 MB」的限制**，也没有单实例的并发上传限制。

**影响**：一个账号可以持续写入 50MB 视频直到磁盘打满（服务器上还跑着别的项目，
磁盘写满是**跨项目**故障）。图片即使被压缩，也挡不住并发。

**修复方案**：`t_user_upload_stat(user_id, day, bytes, count)` 或在内存里按 userId 计数，
单用户日上限 100MB / 50 次；超限 429。同时给 `UPLOAD_DIR` 所在分区加磁盘告警。
